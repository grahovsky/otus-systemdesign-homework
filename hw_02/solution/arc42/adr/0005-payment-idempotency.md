# ADR-0005 — Idempotency-Key для платёжных мутаций

- **Status**: Accepted
- **Date**: 2026-07-12
- **Decision makers**: grahovsky

## Context

Клиент, Gateway и Payment Provider ретраят запросы. Без идемпотентности —
двойное списание или двойной refund. Webhook'и тоже могут дублироваться.

## Decision

Все мутации Payment (`Authorize`, `Capture`, `Refund`) требуют заголовок
**`Idempotency-Key`** (UUID), уникальный в рамках платежного намерения.

- Первый запрос выполняется, результат сохраняется в `db-payment`
- Повтор с тем же ключом → тот же ответ без повторного вызова провайдера
- Webhook обрабатывается по `provider_event_id` (дедуп)

Booking передаёт стабильный ключ, производный от `booking_id + step`
(например `auth:{booking_id}`), чтобы ретраи саги были безопасны.

## Consequences

### Позитивные

- Безопасные ретраи сети и саги
- Предсказуемое поведение при дублях webhook

### Негативные / trade-offs

- Нужно хранить ответы/ключи (TTL или бессрочно для финансов — политика retention)
- Клиент обязан не переиспользовать ключ для другой операции

### Риски

- Разные ключи на один логический платёж → двойное списание; контракт API
  и SDK должны это запрещать/документировать

## Alternatives considered

### Полагаться только на идемпотентность провайдера

Недостаточно: нужны локальные гарантии до вызова и при внутренних ретраях.

### Дедуп только по booking_id без ключа

Ломается, когда на одну бронь легитимны несколько операций (partial refund и т.п.).
