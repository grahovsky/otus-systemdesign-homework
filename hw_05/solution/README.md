## Отказоустойчивость

### 1. RTO / RPO по сервисам

Тир задаём по цене простоя и цене потери данных: что произойдёт с
гостем и с деньгами, если компонент недоступен N минут, и что произойдёт, если последние
записи не долетели после сбоя.

- **Tier 0** — прямой денежный или продуктовый ущерб есть немедленно и накопительно: гость не
  может забронировать/оплатить, либо система рискует продать один номер дважды (overbooking).
- **Tier 1** — деградация заметна, но продукт не встаёт: старые данные, кэш, чуть более долгий
  путь восстановления не блокируют бронирование.
- **Tier 2** — сервис асинхронный или не хранит собственных бизнес-данных; его недоступность не
  останавливает саму бронь.

| Сервис / компонент | Tier | RPO | RTO | Обоснование |
|---|---|---|---|---|
| **Booking** (`db-booking`, saga-оркестратор) | 0 | ≈ 0 | минуты | Хранит статус саги и transactional outbox. Потеря последних коммитов после failover расходит статус брони с Inventory/Payment (бронь зависла между шагами) — руками не восстановить дешево, нужна ручная сверка по каждой записи. RTO в минутах — Booking на пути каждого создания/отмены брони, дольше простой = гости не могут забронировать вовсе. |
| **Inventory** (`db-inventory`, SoT слотов) | 0 | ≈ 0 | минуты | Единственный writer availability/hold ([ADR-0003](../../hw_02/solution/arc42/adr/0003-inventory-soft-hold.md)). Потеря подтверждённого hold/release после сбоя — прямой путь к overbooking (продали то, чего по факту не было, или наоборот заморозили свободный слот навсегда). Цена ошибки выше цены синхронной записи. |
| **Payment** (`db-payment`, intents + idempotency) | 0 | 0 | минуты | Деньги и `idempotency_keys`/`webhook_events`. Потерянная запись об уже принятом платеже или об идемпотентном ключе после failover — риск двойного списания или пропущенного capture. RPO = 0 обязателен независимо от цены задержки на commit; RTO в минутах — сверх того есть reconciliation-job Booking↔Payment ([риск отмечен в модели](../../hw_02/solution/architecture/model/booking/index.c4)) как второй рубеж защиты от рассинхрона с провайдером. |
| **Kafka** (шина: `catalog.*`, `inventory.*`, `booking.*`, `payment.*`) | 0 | ≈ 0 (для подтверждённых записей) | минуты | Через неё едёт outbox всех write-сервисов саги. Потеря неподтверждённого (не replicated) события — пропущенный шаг саги (например, `inventory.released` не дошёл до Booking, бронь не закрылась). Реплицируем синхронно внутри кластера (`acks=all`, RF=3), а не как «просто очередь». |
| **Catalog** (`db-catalog`) | 1 | минуты | десятки минут | Партнёрские данные (объекты, тарифы). Пишет партнёр, редко и не в моменте гостя. Просадка на десятки минут не блокирует уже идущие бронирования — только обновление контента. |
| **Identity** (`db-identity`) | 1 | минуты | десятки минут | Учётные данные и роли. JWT — короткоживущий и проверяется локально на Gateway, поэтому недоступность Identity не обрывает уже залогиненные сессии — только новые логины/регистрации. |
| **Search** (OpenSearch, read-model) | 1 | часы (по факту — восстановимо без потерь) | десятки минут | Не SoT доступности ([ADR-0004](../../hw_02/solution/arc42/adr/0004-cqrs-search.md)) — производный индекс, полностью пересобираемый из Kafka-топиков (retention 7 дней) и Catalog/Inventory. Формальный RPO высокий, но фактическая потеря данных = 0, т.к. это replay, а не восстановление уникальных данных. Итоговая проверка доступности — всё равно `Hold` в Inventory, а не поиск. |
| **Notification** (consumer, без своей БД) | 2 | минуты | минуты | Stateless consumer Kafka. Задержка письма/SMS на несколько минут не блокирует бронь и не теряет данные — offset двигается дальше, событие можно переиграть. |
| **API Gateway** | 2 | не применим (нет бизнес-данных) | минуты | Stateless edge: TLS/JWT/rate-limit. Пересоздаётся из образа за балансировщиком за минуты; данных, которые можно потерять, у него нет. |
| **Redis** (кэш Search/Gateway, hold TTL index) | 2 | не применим (не SoT) | минуты | Ускоряющий слой. SoT для hold всё равно Postgres ([ADR-0003](../../hw_02/solution/arc42/adr/0003-inventory-soft-hold.md)) — полная потеря Redis это холодный кэш и временную доп. нагрузку на TTL-sweeper по Postgres, а не потерю бронирований. |

Не «0 для всего»: у Notification/Gateway/Redis RPO не имеет смысла ужимать до нуля — там нет
уникальных данных, которые можно потерять, а искусственно жёсткий RTO там просто переплата за
избыточность там, где отказ незаметен пользователю. У Payment он ровно 0, потому что цена
ошибки (двойное списание/утерянный платёж) кратно выше цены синхронной репликации.

### 2. Репликация критичных БД

Критичные БД — три отдельных PostgreSQL-кластера Tier 0 (`db-booking`, `db-inventory`,
`db-payment`, [ADR contexts ДЗ 2](../../hw_02/solution/architecture/model/booking/index.c4)).
Каждый — **свой** кластер (database-per-service, [ДЗ 3](../../hw_03/solution/)), но схема HA у
всех трёх одинаковая — показана один раз на [`diagrams/replication-ha.puml`](diagrams/replication-ha.puml).

Схема читается через три плоскости HA-решения:

| Плоскость | Решение | Почему |
|---|---|---|
| **Data plane** | Физическая репликация (WAL), не логическая | Стандарт HA для PostgreSQL; идентичная байт-в-байт копия, не нужна трансформация потока (в отличие от CDC/логической, которая нужна была бы для миграции движка или выборочной репликации) |
| **Data plane — режим ACK** | Внутри региона (AZ1→AZ2) — **semi-sync/кворумный** ACK. В другой регион (DR) — **асинхронно** | Частый гибрид: кворум внутри площадки даёт RPO ≈ 0 без межрегионального RTT на каждый commit; async-реплика в другом регионе — только на случай потери всего региона, где RPO в минуты уже приемлем (см. п.1) |
| **Control plane** | Внешний оркестратор (Patroni-подобный) + кворум в DCS (etcd/Consul, 3+ узла) + fencing | RTO нужен в минутах ([п.1](#1-rto--rpo-по-сервисам)) — ручной failover дежурным (RTO десятки минут+) сюда не подходит. Кворум + fencing — обязательное условие автоматического failover, иначе при разрыве сети получаем **split brain**: два primary принимают записи, потом расходящиеся данные сливаются вручную и с потерями — это хуже простоя |
| **Routing plane** | Прокси-слой (writer/reader hostgroups) перед приложением | Приложение не хранит адрес текущего лидера и не участвует в election; после failover прокси сам переключает hostgroups. Прокси зарезервирован отдельно (пара + VIP) — иначе он сам становится новым SPOF |

**Почему не distributed SQL / multi-leader:** саге Booking достаточно одного writer на кластер
(inventory/booking изначально спроектированы без cross-shard записи, [ДЗ 3](../../hw_03/solution/#2-шардирование));
операционная цена CockroachDB/Spanner-класса решений не окупается при текущей нагрузке (пик
записи ~25 RPS, [ДЗ 4](../../hw_04/solution/#1-расчёт-rps)). Managed Multi-AZ (primary + sync
replica «в один клик») здесь операционно безопаснее самодельного кластера.

**Остальная инфраструктура** (не Tier 0, но участвует в устойчивости):

| Компонент | Репликация | Комментарий |
|---|---|---|
| **Kafka** | RF = 3, `acks=all`, `min.insync.replicas=2` | Подтверждённая (acked) запись переживает потерю одного брокера без потери события — обязательное условие RPO ≈ 0 из п.1 для событий саги |
| **Redis** | Sentinel (авт. failover) | Не SoT ([ADR-0003](../../hw_02/solution/arc42/adr/0003-inventory-soft-hold.md)) — полная потеря узла не теряет бизнес-данные, только прогретый кэш |
| **OpenSearch** | 3 реплики шардов на разных нодах | Восстановимо полностью из Kafka + Catalog/Inventory даже при потере всех реплик — но реплики держим, чтобы не пересобирать индекс на каждый чих ([ДЗ 3](../../hw_03/solution/)) |

Разделение ответственности с бэкапами и DR: то, что показано на этой схеме — **за
продолжение работы** (availability) при отказе процесса/узла/зоны. От логической ошибки
(`DELETE`/баг миграции — реплицируется на все копии так же исправно, как и корректные данные)
и от потери всего региона это не защищает — это отдельные контуры, см. п.4 (план DR).
