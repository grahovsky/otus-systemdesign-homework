## 1. План нагрузочного тестирования

Профиль нагрузки используем без пересчёта — тот, что уже получен в
[`sizing.md` §1](sizing.md#1-расчёт-rps): Ingest **370 / 1 111 HTTP** (среднее/пик),
поток событий **3 704 / 11 111 соб/с**, Query API ~**3 RPS**. HTTP ≠ throughput: средний
батч 10 событий ([`sizing.md` A1](sizing.md)). Дополнительно учитываем потолок из
[`sizing.md` §5](sizing.md#5-оптимизация): hotspot-приложение (**2%** потока, A14) кладётся
на один шард `app_id` и даёт скан ~36 ГБ сжатых / ~7 с — **выше** SLO p95 < 2 с. Это не
общесистемный RPS, а конкурентная нагрузка на один `app_id`; именно она способна нарушить
G1, а не абсолютное число запросов по системе в целом.

Парк — [6 инстансов Ingest](sizing.md#4-оценка-ресурсов-и-стоимости) × 400 RPS с запасом ×2:
в пике занято `1 111 / 400 ≈ 2.8` инстанса, остальные — отказ и выкатка.

| # | Сценарий | Профиль нагрузки | Длительность | Что проверяем |
|---|---|---|---|---|
| 1 | Smoke / baseline | среднее: 370 HTTP / 3 704 соб/с | 10 мин | окружение и тестовые данные корректны, метрики и алерты ([`observability.md` §1–2](observability.md#1-ключевые-метрики)) собираются, прежде чем переходить к пиковому профилю |
| 2 | Load — целевой пик | 1 111 HTTP / 11 111 соб/с, распределены по 2 000 `app_id` как в сайзинге | 30–60 мин, устойчиво | парк из 6 Ingest держит целевой пик в рамках SLO без ручного вмешательства; Storage Writer flush раз в 2 с ([`sizing.md` A11](sizing.md)), consumer lag (#8) не растёт |
| 3 | Hotspot (главный риск) | одно приложение = **2%** потока (A14) на фоне load; query-time воронка по его 90 дням (~36 ГБ сжатых). Отдельно — превышение per-app лимита этим же `app_id` | 5–10 мин на query; запись — на фоне load | **главная проверка**: скан hotspot ~7 с, чужие `app_id` на другом шарде остаются в p95 < 2 с, ingest остальных не деградирует. 429 на шумном `app_id` — успех bulkhead, не ошибка теста ([`reliability.md` §3](reliability.md#3-паттерны-отказоустойчивости)). Per-app лимит выше штатных 2% и ниже доли, способной занять парк Ingest — конкретное число RPS в модели не фиксируем, проверяем изоляцию, а не калибровку порога |
| 4 | Stress — за пределами пика | плавный рост от 1 111 HTTP до отказа | до появления ошибок/деградации | где реальная точка отказа относительно проектных 6 × 400 RPS; совпадает ли узкое место с предсказанным (Ingest / Writer / parts ClickHouse, не Query RPS — его ~3) |
| 5 | Spike | ступень 370→1 111 HTTP за секунды (суточный peak factor ×3) и шторм одного `app_id` сверх per-app лимита | всплеск 2–5 мин | 429 локализованы на шумном приложении (метрика #2), 5xx не растут; p99 ingest не разгоняет сам себя ретраями SDK (алерт «p99 ingest выше SLO») |
| 6 | Soak / выносливость | целевой пик 1 111 HTTP / 11 111 соб/с без остановки | 4–8 часов | то, что не видно за 30 минут: рост parts pending merge (#10), eviction окна дедупа (#11), дрейф Kafka lag Writer (#8), появление DLT (#5), утечки памяти Ingest/Writer, диск/логи не переполняются |

**Метрики успеха** (те же метрики и пороги, что в
[`observability.md` §1–2](observability.md#1-ключевые-метрики), не отдельный набор «для теста»):

- Ingest: доля 5xx + таймаутов < 0.5% за 3 мин (метрика #2 / алерт «Рост ошибок приёма»),
  p99 `POST /v1/events` < 300 мс (метрика #3).
- 4xx / 429 / `SCHEMA_VIOLATION` не считаем ошибкой теста — ожидаемое поведение bulkhead
  и клиентской схемы. 429 на одном `app_id` при живом ingest остальных — успех изоляции,
  не нехватка парка.
- Storage Writer: DLT = 0 на валидных батчах (метрика #5 / алерт «Рост DLT»); consumer lag
  не растёт на load/soak и возвращается к нулю после снятия нагрузки (warning > 15 мин,
  метрика #8).
- Redis: eviction ключей `event:` = 0 при слоте 32 ГБ (метрика #11; расчёт пика окна
  ~19 ГБ, [`sizing.md` A9](sizing.md)).
- Query средних приложений: p95 < 2 с (метрика #6). Запрос hotspot-приложения **не** обязан
  уложиться в 2 с — критерий сценария 3: фактическое время порядка ~7 с и изоляция шарда
  (чужие `app_id` в SLO). Если hotspot укладывается в 2 с на полном объёме — опровергается
  оценка [`sizing.md` §5](sizing.md#5-оптимизация); если чужие приложения деградируют вместе
  с ним — опровергается локальность ключа [ADR-0004](arc42/adr/0004-shard-by-app-id.md).
- G3: повтор того же `event_id` не увеличивает `count()` в `events` — дедуп Redis и
  идемпотентный INSERT ([ADR-0002](arc42/adr/0002-idempotency-not-exactly-once.md)).
- После окончания нагрузки система возвращается к штатным метрикам за время, сравнимое
  с RTO compute-уровня (минуты, [`reliability.md` §1](reliability.md#1-rto--rpo-по-сервисам)) —
  не требует ручного восстановления.

**Данные теста.** Синтетический поток того же порядка, что в
[`sizing.md` §1](sizing.md#1-расчёт-rps). Для сценария 3 обязателен заранее выделенный
hotspot-`app_id` с объёмом ~36 ГБ сжатых за 90 дней — без него проверка §5 фиктивна, а
именно этот скан и есть проектное узкое место, не общий RPS. Полные 2.3 ТБ сырья на все
2 000 приложений для ingest-сценариев (1–2, 4–6) не обязательны: приём сайзится по RPS,
не по глубине истории. Объём hotspot-приложения для query не ужимаем — иначе ~7 с
не воспроизвести.

## 2. Chaos-эксперименты

Три эксперимента проверяют три разных механизма отказоустойчивости, а не один и тот же
способ отказа три раза: кворумная вставка и routing реплик ClickHouse
([`reliability.md` §2](reliability.md#2-репликация-критичных-хранилищ)), circuit breaker и
stale-кэш против деградации App & Config
([ADR-0005](arc42/adr/0005-ingest-config-degraded-mode.md),
[`reliability.md` §3](reliability.md#3-паттерны-отказоустойчивости)), at-least-once доставку
через буфер Kafka и идемпотентный INSERT
([`reliability.md` §1](reliability.md#1-rto--rpo-по-сервисам),
[`data-storage.md` §5](data-storage.md#5-очереди--асинхронность-на-хранении)).

Точки отказа на пути записи — [`diagrams/chaos-faults.puml`](diagrams/chaos-faults.puml):
три разных компонента, не три kill одного инстанса. Региональный DR сюда не входит: он
закрывается game day из [`reliability.md` §4](reliability.md#4-план-dr).

```
Эксперимент №1: отказ одной реплики шарда ClickHouse
Steady state:    INSERT Writer в норме (метрика #4), DLT = 0 (#5), p95 Query средних
                 приложений < 2 с (#6), ingest 5xx и p99 в пороге алертов (#2, #3)
Гипотеза:        при insert_quorum=2 и двух репликах шарда потеря одной реплики останавливает
                 ACK вставки — иначе заявленный локальный RPO ≈ 0 был бы фикцией. Ingest
                 продолжает принимать батчи (HTTP 202): развязка от ClickHouse заложена в
                 ADR-0001, а не в кворуме. Writer уходит в retry, не в DLT, на время
                 локального RTO 5 мин, пока реплика не вернётся. Query читает с живой реплики
                 шарда (routing plane §2) — средние приложения остаются в p95 < 2 с
Blast radius:    staging, один шард ClickHouse (одна реплика из двух), заранее объявленное
                 окно, авто-abort по таймеру. Соседний шард и Kafka не трогаем
Метод:           контролируемо остановить процесс одной реплики шарда (kill -9 / отключить
                 инстанс) через chaos-инструмент, затем вернуть её в пределах окна RTO
Наблюдаем:       отказ кворума / lag реплики (#10); рост retry Writer без роста DLT (#5);
                 ingest accepted (#12) не проседает; p95 Query средних не уходит за 2 с;
                 время восстановления вставки vs целевой RTO 5 мин из §1
Rollback:        сообщения в DLT, либо ingest 5xx (развязка ADR-0001 не сработала), либо
                 восстановление кворума не произошло за 2×RTO — немедленно поднять реплику
                 вручную, main соседних партиций не останавливать
Ожидаемый вывод: фактическое поведение кворума и развязки ingest↔ClickHouse против заявленных
                 в §1–2 — подтверждение или повод пересмотреть RTO Writer / порог DLT.
                 Если INSERT продолжается при одной живой реплике — quorum на практике не
                 равен 2, и локальный RPO ≈ 0 не выполняется
```

```
Эксперимент №2: недоступность App & Config
Steady state:    ingest 5xx и p99 в норме (метрики #2–3, алерты «Рост ошибок приёма» /
                 «p99 ingest выше SLO»), accepted/мин стабилен (#12)
Гипотеза:        timeout + circuit breaker + stale-кэш (ADR-0005, §3) не дадут простою
                 App & Config (Tier 1) эскалировать в потерю событий на Ingest (Tier 0):
                 уже известные app_id обслуживаются из просроченного кэша в пределах
                 30 мин сверх TTL 5 мин; p99 не упирается в timeout fallback. Новые app_id
                 без записи в кэше — fail-closed сразу: безопасного значения ключа/схемы
                 по умолчанию нет. Bulkhead раздельных пулов не отдаёт соединения produce
                 в Kafka под зависший fallback
Blast radius:    staging, только исходящие вызовы Ingest → App & Config, ограниченное окно
                 короче 30-минутного бюджета stale (чтобы не доводить известные app_id до
                 fail-closed массово)
Метод:           fault injection на fallback-вызов: сначала +300–500 мс задержки, затем
                 полный timeout / недоступность App & Config
Наблюдаем:       тег открытия circuit breaker на спане Ingest (observability §3);
                 p99 ingest выходит на плато после открытия breaker, а не растёт к таймауту
                 каждого батча; 5xx известных приложений не растут; батчи новых app_id
                 отклоняются; utilization пула Kafka producer не меняется (bulkhead держит)
Rollback:        5xx или просадка accepted у уже закэшированных app_id, либо p99 устойчиво
                 выше 300 мс — немедленно снять fault injection. Если деградация перешла
                 на produce в Kafka — изоляции пулов нет, эксперимент останавливаем
Ожидаемый вывод: подтверждение или опровержение stale-режима и своевременности breaker.
                 Если известные приложения начинают получать 5xx сразу после промаха кэша —
                 ADR-0005 на практике не работает, и Tier 1-сбой уже есть Tier 0-потеря
```

```
Эксперимент №3: lag consumer group Storage Writer
Steady state:    consumer lag группы Writer ≈ 0 (метрика #8), DLT = 0 (#5), freshness
                 INSERT в минутах, не в часах (#13)
Гипотеза:        при временном лаге принятые батчи не теряются (RF=3, acks=all, retention
                 12 ч, §1–2) — Ingest продолжает отвечать 202; обработка наверстывает после
                 возврата консьюмеров; повторное чтение не создаёт дублей в events
                 (идемпотентный INSERT, ADR-0002). Один оставшийся Writer не разгребает
                 чужой шард: партиции остановленного инстанса отстают отдельно — проверка
                 и того, что retry/DLT не смешивает шарды (data-storage §5)
Blast radius:    staging, только consumer group Storage Writer (2 инстанса — по шарду),
                 окно 10–15 мин с последующим восстановлением — много меньше половины
                 retention (6 ч из 12, порог critical лага)
Метод:           остановить N−1 из N инстансов Writer (1 из 2), дать очереди накопиться
                 на партициях остановленного шарда, затем вернуть на полную мощность
Наблюдаем:       рост lag на затронутых партициях (алерт «Lag Storage Writer» на пороге
                 15 мин, если окно это допускает; на 10–15 мин — сам факт роста и отсутствие
                 critical); ingest accepted не проседает; после восстановления — скорость
                 наверстывания (lag → 0) и сверка count() по app_id / окну received_at
                 против accepted Ingest (нет потери, нет лишних строк)
Rollback:        lag не начинает падать после возврата Writer, либо появляются сообщения
                 в DLT, либо count в events расходится с accepted — остановить нагрузку
                 и запустить ручной replay из retry/DLT с дедупом по event_id; main
                 соседних партиций не останавливать
Ожидаемый вывод: подтверждение at-least-once доставки и способности пути в SoT пережить
                 временный простой Writer без потери принятых событий — плюс фактическое
                 время наверстывания при известном объёме накопленного лага. Если после
                 восстановления в events больше строк, чем accepted уникальных event_id —
                 второй барьер идемпотентности не сработал
```
