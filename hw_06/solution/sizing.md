## Исходные параметры и допущения

Цифры нагрузки — из [`requirements.md` §1.2](requirements.md#12-нефункциональные-требования).
1 ТБ = 1000 ГБ. Пик внутри суток — `×3`, повторно на рост аудитории не умножается.

| Параметр | Значение | Как используем |
|---|---|---|
| Приложений-клиентов | 2 000 | метаданные App & Config, Query API, стоимость на клиента |
| MAU (конечные пользователи приложений) | 50 000 000 | не единица нагрузки: запись считается от событий |
| DAU | 8 000 000 | fetch конфига SDK и оценка hotspot-приложения |
| Событий на DAU в сутки | 40 | `событий/сутки = DAU × 40` |
| Событий/сутки | 320 000 000 | единица для RPS хранилища, Kafka, ClickHouse, bandwidth |
| Размер события до сжатия | 0.5 КБ | диск и полоса до gzip / колоночного сжатия |
| Батч SDK | до 50 событий или раз в 30 с | HTTP RPS Ingest ≠ событийный throughput |
| Retention сырых | 90 дней | окно, не копится |
| Retention агрегатов DAU/MAU | 2 года | копится, но не как сырьё |
| Peak factor | ×3 | суточный профиль (утро/вечер) |

```
событий/сутки        = 8 000 000 × 40              = 320 000 000
RPS событий среднее  = 320 000 000 / 86 400     = 3 704
RPS событий в пике   = 3 704 × 3                 = 11 111
```

### Допущения (можно оспорить)

| # | Что подставили | Зачем |
|---|---|---|
| A1 | Средний батч SDK — **10 событий**, не 50 | 40 событий/DAU размазаны по сессиям; срабатывает таймер 30 с, не потолок 50. Меньший батч даёт больший HTTP RPS — консервативно для Ingest |
| A2 | Fetch конфига SDK — **2 раза / DAU / сутки** | Конфиг при старте сессии; типичный consumer-mobile — утренняя и вечерняя сессия, в одной линии с суточным пиком ×3 |
| A3 | gzip входящего JSON **×5** | Типичное сжатие JSON с фиксированными ключами (4–6×); HTTP-обвязка сверху **+10%** |
| A4 | Колоночное сжатие ClickHouse **×8** к JSON 0.5 КБ | Фиксированная схема без произвольных properties ([§1.2](requirements.md#12-нефункциональные-требования)); высокая кардинальность `user_id` не даёт 15×, но 8× для MergeTree с низкокардинальными атрибутами — ожидаемый порядок |
| A5 | Накладные MergeTree (marks, primary index, parts) **×1.3** к сжатому | Не путать с ×2.5 строчных СУБД из другого класса систем: WAL/индексы Postgres здесь не применяются |
| A6 | Аудитория и поток событий **+25%/год** | В NFR роста нет; закладываем, чтобы диск и Ingest к году 3 не считать «как сейчас». Пик ×3 уже внутри суток, на рост не умножается повторно. `1.25³ ≈ 1.95` |
| A7 | Query API: **2 аналитика на приложение × 20 запросов/сутки** | 2 000 × 2 × 20 = 80 000 запросов/сутки. Даже ×10 не меняет парк: чтение аналитики не hot path |
| A8 | Cache-aside API-ключа/схемы: hit **99.5%**, TTL 5 мин | 2 000 ключей, ротация редкая; промах Ingest → App & Config не сайзится как отдельная нагрузка |
| A9 | Окно дедупа `event_id` в Redis — **TTL 6 ч**, ~80 Б на ключ | TTL больше retry-budget SDK (минуты) и покрывает несколько часов офлайна устройства ([ADR-0002](arc42/adr/0002-idempotency-not-exactly-once.md)); 24 ч раздуло бы Redis без выигрыша для аналитики |
| A10 | Kafka `events.raw`: retention **12 ч**, RF = 3, сжатие брокера **×4** | «Несколько часов простоя writer» из [§1.3](requirements.md#13-риски-и-ограничения); 12 ч — ночной инцидент, не недельный архив |
| A11 | Storage Writer: flush **каждые 2 с или 100 000 событий** | Пик 11 111 соб/с → ~22 тыс. строк в INSERT. Закрывает антипаттерн мелких INSERT ([ADR-0001](arc42/adr/0001-batch-insert-clickhouse.md)) |
| A12 | Шард ClickHouse по `app_id`; на старте **2 шарда × 2 реплики** | `ORDER BY (app_id, event_time)` из модели контейнера. 11 111 insert/s одну реплику не перегружают; больше шардов hotspot-приложение не ускоряет (оно целиком на одном шарде) |
| A13 | MV DAU/MAU на 2 года: `(app_id, date, platform, version)` + HLL (~4 КБ/группа), **без `country`** | Страна остаётся query-time по сырью 90 дней. Иначе HLL на `(app × страна × платформа × версия)` раздувает агрегат до сотен ГБ |
| A14 | Самое нагруженное приложение — **2%** всех событий | 2 000 клиентов; равномерность нереалистична. 2% — крупное consumer-приложение (~400k DAU при 40 событиях), не «среднее × 1» |
| A15 | 4 vCPU ≈ 1000 RPS простых HTTP; Ingest **~400 RPS** на такой инстанс; запас **×2** (отказ и выкатка) | Справочник занятия по сайзингу. Ingest тяжелее простого HTTP: gzip, разбор JSON, pipeline в Redis, produce в Kafka |

## 1. Расчёт RPS

Единица системы — **событие**. HTTP-запрос SDK — батч (A1). Сайзим Kafka / Storage Writer / ClickHouse по событиям; Ingest API — по HTTP.

### Запись: события и Ingest API

```
батчей/сутки     = 320 000 000 / 10           = 32 000 000
HTTP ingest ср.  = 32 000 000 / 86 400        = 370
HTTP ingest пик  = 370 × 3                   = 1 111
```

| Что | N/сутки | Формула | среднее | **пик** |
|---|---|---|---|---|
| События (throughput) | 320M | DAU × 40 | 3 704 | **11 111** |
| `POST` батча в Ingest API | 32M | 320M / 10 | 370 | **1 111** |
| Produce в Kafka | 32M батчей / 320M событий | одно сообщение = батч; сайзим брокер по 11 111 соб/с | 3 704 соб/с | **11 111** соб/с |
| INSERT в ClickHouse | flush раз в 2 с (A11) | 11 111 × 2 ≈ 22 тыс. строк/INSERT | ~0.5 INSERT/с на writer | **~0.5** INSERT/с |

Fan-out батча (в сумму клиентского RPS не входит): 1 GET ключа + 1 INCR rate-limit + 10 SET `event_id` в Redis + 1 produce в Kafka. Кэш ключа внутри Ingest, не на отдельном Gateway — Gateway в составе нет ([`architecture/README.md`](architecture/README.md)).

Промах кэша ключа/схемы (A8): `1 111 × 0.5% ≈ 6` RPS в пике на App & Config — на фоне fetch конфига SDK не видно.

### Чтение: конфиг SDK и Query API

```
fetch конфига / сутки = 8 000 000 × 2         = 16 000 000
Query / сутки         = 2 000 × 2 × 20        = 80 000
```

| Что | N/сутки | среднее | **пик ×3** |
|---|---|---|---|
| `GET` sdk-config (App & Config) | 16M | 185 | **556** |
| Query API (4 эндпоинта суммарно) | 80k | 0.9 | **3** |
| CRUD владельца (ключи, definitions) | ≪ 10k | < 0.1 | **< 1** |

Запись (события) на порядки больше аналитического чтения: это обратная картина к интерактивному user-facing сервису. Query API упирается в **объём сканирования ClickHouse**, не в число HTTP-запросов.

Периодическая проверка alert-правил ([ADR-0006](arc42/adr/0006-threshold-alerts-webhook.md)) —
не новая RPS-статья. Оценка: 2 000 приложений × до 2 правил ≈ 4 000 проверок раз в 15 мин
→ ≈ 4.4 запроса/с к ClickHouse тем же путём, что sync Query. Это того же порядка, что пик
~3 HTTP Query API (A7), и на фоне ingest 1 111 HTTP / 11 111 соб/с не видно. Парк Query из
двух инстансов не пересматриваем: узкое место по-прежнему чтение hotspot-приложения (§5,
на границе SLO), а не число правил. Cooldown per-rule ограничивает исходящий webhook при массовой просадке.

### Redis (hot path Ingest)

| Операция | среднее | пик | Формула |
|---|---|---|---|
| Redis ops (ключ + rate-limit + дедуп) | ~4 400 | **~13 300** | 12 команды на батч × 370 / 1 111 |
| Промах → App & Config | ~2 | **~6** | 0.5% батчей |

13 тыс. ops/s для Redis — не узкое место; память окна дедупа — отдельная строка в §2.

### Сводка (вход в сервис)

| | среднее | **пик ×3** |
|---|---|---|
| **События (Kafka / Writer / CH insert)** | 3 704 соб/с | **11 111 соб/с** |
| **Ingest API (HTTP)** | 370 | **1 111** |
| **App & Config (HTTP)** | ~190 | **~560** |
| **Query API (HTTP)** | ~1 | **~3** |

В пике упираемся в **приём и запись событий**, не в дашборд. Одновременно висящих HTTP Ingest: `1 111 × 0.3 с (p99) ≈ 330` in-flight — пул соединений, не кластер.

## 2. Расчёт хранилища

Накладные ClickHouse — **×1.3 к сжатому** (A5), не ×2.5 строчной СУБД. Вторая копия — купленный диск реплики. Kafka и Redis не копятся.

### Сырые объёмы (сейчас)

```
сырой поток              = 320e6 × 0.5 КБ            = 160 ГБ/сутки
ClickHouse сжатие ×8    = 160 / 8                    = 20 ГБ/сутки
+ marks/parts ×1.3      = 20 × 1.3                   = 26 ГБ/сутки
сырьё 90 дней            = 26 × 90                   = 2.3 ТБ / реплика

MV DAU/MAU (A13)         = 2 000 × 2 × 4 × 730 × 4 КБ ≈ 47 ГБ   ← 2 года, не 90 дней
Postgres метаданные      = 2 000 × ~20 КБ             ≈ 40 МБ   ← не от потока событий
Kafka 12 ч (A10)         = (160 / 4) × 0.5 × RF=3     = 60 ГБ
Redis дедуп (A9)         = 3 704 × 6 × 3 600 × 80 Б    ≈ 6.4 ГБ среднее;
                           11 111 × 6 × 3 600 × 80 Б   ≈ 19 ГБ в пике  → слот 32 ГБ
```

MV: 2 000 приложений × 2 платформы × 4 активные версии × 730 дней × 4 КБ HLL. `country` в этот агрегат не входит (A13).

### С накладными и ростом +25%/год (A6)

Сырьё — **окно 90 дней**: растёт суточный поток, не «× 90 × годы». MV — копится в горизонте 2 лет; к году 3 окно по-прежнему 2 года, растёт кардинальность групп (новые приложения/версии) и поток.

| Где | Сейчас | 1 год (×1.25) | 3 года (×1.95) | Копится? |
|---|---|---|---|---|
| ClickHouse сырьё (90 д, 1 реплика) | **2.3 ТБ** | **2.9 ТБ** | **4.6 ТБ** | окно × рост потока |
| ClickHouse MV DAU/MAU (2 года) | **~50 ГБ** | **~60 ГБ** | **~100 ГБ** | да, в пределах 2 лет |
| PostgreSQL | 50 ГБ слот | 50 ГБ | 50 ГБ | нет (метаданные) |
| Redis (дедуп + кэш ключей) | **32 ГБ** слот | 32 ГБ | **64 ГБ** | нет, окно 6 ч × поток |
| Kafka (12 ч, RF=3) | **60 ГБ** | 75 ГБ | **120 ГБ** | нет |
| **Итого диск CH (2 реплики)** | **4.7 ТБ** | **5.9 ТБ** | **9.4 ТБ** | сырьё, не MV |

Через 3 года место ест **окно сырых событий**, не Postgres и не MV. Календарный «× 3 года» к сырью не применяется: TTL 90 дней.

Hotspot (A14): 2% × 320M = 6.4M событий/сутки × 90 = 576M событий ≈ 288 ГБ несжатых ≈ **36 ГБ сжатых** на одном `app_id` — объём **всего ряда** на диске (`0.5 КБ / 8 = 64 Б` на событие). Сколько из этого читает запрос — в §5. В закупку диска цифра не входит: она уже внутри 2.3 ТБ сырья.

## 3. Расчёт bandwidth

Загрузка в облако (ingress) обычно не тарифицируется; в счёте — **egress**. Медиа и CDN нет: наружу уходят JSON-ответы.

### За сутки (среднее)

```
вход до gzip         = 160 ГБ/сутки
вход после gzip ×5  = 32 ГБ/сутки
+ HTTP-обвязка +10%  = 35 ГБ/сутки                 ← ingress, в счёт не кладём

ack Ingest           = 32e6 × 0.5 КБ             = 16 ГБ/сутки
sdk-config           = 16e6 × 2 КБ               = 32 ГБ/сутки
Query API            = 80e3 × 20 КБ              = 1.6 ГБ/сутки
egress суммарно      ≈ 50 ГБ/сутки  ≈ 1.5 ТБ/мес
```

В пике те же потоки **×3**. Картинок нет — сезонного «×5 на CDN» тоже нет.

### Пиковая полоса

Полоса — в **битах** (Мбит/с). В счёте платим за **гигабайты** egress.

```
ingress (gzip):  35×10^9 × 8 / 86 400            ≈ 3.2 Мбит/с
пик ingress:     3.2 × 3                        ≈ 10 Мбит/с

egress:          50×10^9 × 8 / 86 400           ≈ 4.6 Мбит/с
пик egress:      4.6 × 3                        ≈ 14 Мбит/с
```

| Что | ГБ/мес | Пик | Откуда счёт |
|---|---|---|---|
| Ingress (батчи gzip) | ~1 050 | 10 Мбит/с | бесплатно |
| Egress (ack + config + query) | **~1 500** | **~14 Мбит/с** | наши серверы |
| CDN / объектное | 0 | — | нет медиа |

Полоса не является ограничением и не является статьёй счёта. Узкое место — не канал.

## 4. Оценка ресурсов и стоимости

Цены — справочник занятия по сайзингу. Месяц = 730 часов. Managed ≈ **×2** к VM+диску. На 100% загрузки не проектируем.

**Больше 2 шардов ClickHouse на старте не берём (A12):** insert 11 111 соб/с диск не перегружает; добавление шардов не ускоряет запрос по одному `app_id`.

### Сервисы без своего состояния (пик, верхняя оценка)

К году 3 поток ×1.95: Ingest 1 111→**2 166**, App & Config 556→**1 084**, события 11 111→**21 700**. Query по-прежнему единицы RPS.

| Сервис | RPS/throughput в пике | Ёмкость инстанса | Инстансы (×2) | Размер | Почему столько |
|---|---|---|---|---|---|
| Ingest API | 1 111 HTTP | 400 RPS / 4 vCPU | **6** | 4 vCPU | `1 111 / 400 × 2 ≈ 5.6` → 6 |
| App & Config | 556 HTTP | 1 000 RPS / 4 vCPU | **2** | 4 vCPU | `556 / 1 000 × 2 ≈ 1.1` → две машины минимум; Postgres на 556 мелких чтениях не узкое место |
| Query API | 3 HTTP | тяжёлый запрос к CH, p95 < 2 с | **2** | 4 vCPU | две машины минимум; CPU не считает воронку — считает ClickHouse |
| Storage Writer | 11 111 соб/с | батч 2 с (A11) | **2** | 4 vCPU | две машины (потребители 2 шардов/набора партиций); 11k соб/с не требуют парка |
| **Итого** | | | **12** | | |

К году 3: Ingest `2 166 / 400 × 2 ≈ 10.8` → **12** инстансов; App & Config `1 084 / 1 000 × 2 ≈ 2.2` → **4**. Writer остаётся 2 (21k соб/с, тот же flush 2 с → ~43 тыс. строк/INSERT). Парк **20** инстансов, не 12.

### Managed (базы, кэш, очередь)

| Что | Как стоит | vCPU на ноду | Диск (год 1) |
|---|---|---|---|
| ClickHouse | 2 шарда × 2 реплики = 4 ноды | 4 | 1.5 ТБ ×4 (сырьё 2.3 ТБ×2 реплики + запас ≈ 6 ТБ) |
| Kafka | 3 брокера | 4 | 50 ГБ ×3 (60 ГБ с RF=3 + запас) |
| Redis | 2 ноды (реплика) | 4 | RAM 32 ГБ, не SSD |
| PostgreSQL | основная + реплика | 2 | 50 ГБ ×2 |
| Балансировщики | 2 входа (ingest-host и owner API) | — | — |

ClickHouse 4 vCPU: insert не требует больше; аналитический запрос среднего приложения (160k соб/сутки × 90 ≈ 14M событий ≈ 0.9 ГБ сжатых) укладывается в p95 < 2 с. Hotspot — не решается этим парком, см. §5.

| **ИТОГО** | ≈ **$4 700** | **≈ $6 400** | Ingest и диск CH, не Query и не Postgres |

Одной статьи «80%» нет: **managed ≈ 65%**, из них ClickHouse ≈ $1 560 (треть всего счёта). Сеть ≈ 4% — обратная картина к раздаче медиа.

## 5. Оптимизация

### Узкое место

**Не счёт.** $4.7–6.6k/мес при 2 000 приложениях — не ограничение. Узкое место: **query-time воронка/retention по сырым событиям hotspot-приложения** — на границе SLO, не многократный промах.

Среднее приложение: `320M / 2 000 = 160k` событий/сутки × 90 = 14.4M событий ≈ 7.2 ГБ несжатых ≈ **0.9 ГБ сжатых** (весь ряд). Чтение нужных колонок — доля этого объёма, p95 < 2 с выполняется с запасом.

Hotspot 2% потока (A14): 6.4M событий/сутки × 90 = 576M событий. На диске это ≈ 288 ГБ несжатых ≈ **36 ГБ сжатых** всего ряда (`0.5 КБ / 8 = 64 Б` на событие, `576e6 × 64 Б ≈ 36 ГБ`). Шард по `app_id` (A12) кладёт приложение на **одну** ноду. Последовательное чтение сжатого ~5 ГБ/с с NVMe.

`36 / 5 ≈ 7 с` — **верхняя граница**, не ожидаемое время запроса: столько вышло бы, если бы ClickHouse прочитал все колонки за все 90 дней и не пропустил ни одной гранулы. Funnel и retention читают `event_name`, `user_id`, `event_time`. Порядок сжатого объёма этих колонок (оценка, не бенчмарк): `event_name` ~2 Б (LowCardinality), `event_time` ~2 Б (DateTime64 + delta), `user_id` ~16 Б (высокая кардинальность, слабое сжатие) → **~20 Б/событие**. `576e6 × 20 Б ≈ 12 ГБ`, `12 / 5 ≈ 2.4 с` на окне в 90 дней — **около SLO p95 < 2 с**.

Первичный ключ `(app_id, event_time)` отсекает гранулы вне `[from, to]`: окно W дней читает около `W/90` этих 12 ГБ. Воронка на 7 дней (пример в [`api/analytics-query.md`](api/analytics-query.md)) ≈ `12 × 7/90 ≈ 0.9 ГБ` → ~0.2 с; retention на 30 дней ≈ 4 ГБ → ~0.8 с. Худший случай — запрос на весь горизонт 90 дней ([`requirements.md` §1.2](requirements.md#12-нефункциональные-требования)): колоночное чтение ~2.4 с. Цифра ~7 с эту границу не подменяет.

Дополнительная реплика шарда даёт запас по отказу и не ускоряет чтение одного запроса. Третий и четвёртый шард держат чужие `app_id` и этому запросу не помогают.

Это потолок продукта на текущем ADR-0003 (query-time по сырью): на полном горизонте запрос hotspot-приложения оказывается на границе SLO. 11 111 insert/s и 1 111 HTTP — докупаются инстансами линейно (год 3: 12 Ingest). Запрос hotspot-приложения шардами по `app_id` не ускоряется.

**Не поможет** (уже есть или легко докупить, узкое место не снимает): ещё инстансы Query API — они ждут ClickHouse; ещё реплики на чтение без шардирования запроса; Kafka с большим RF; CDN; урезание TTL Redis.

**Что меняет потолок** (числа — от колоночных 12 ГБ на 90 дней, не от верхней границы 36 ГБ):

1. **Pre-aggregation / MV под воронку hotspot-приложения** — чтение витрины вместо ~12 ГБ колонок (верхняя граница полного ряда — 36 ГБ). Нужен как запас: окно 90 дней уже около SLO, а `uniq(user_id)` по 576M событий добавляет CPU сверх последовательного чтения. Цена: смена funnel definition требует backfill; гибкость definitions, ради которой выбран query-time ([ADR-0003](arc42/adr/0003-query-time-vs-pre-aggregation.md)), на этом клиенте теряется. Имеет смысл как исключение для приложений выше порога, не как замена ADR для всех 2 000.
2. **Шард не по `app_id`, а по `hash(user_id)`** — 12 ГБ раскладываются на 2 шарда, чтение ~1.2 с; на 4 шардах ~0.6 с. По байтам оба варианта уже внутри SLO. Цена: запрос среднего приложения больше не пропускает чужие гранулы одним `app_id`-префиксом и всегда трогает все шарды; средний случай дорожает ради хвоста, который колонками и так около SLO.
3. **Серверный sampling на hotspot (уже есть в продукте как конфиг SDK)** — 50% событий → ~6 ГБ колонок ≈ 1.2 с на окне 90 дней: колоночное чтение укладывается в SLO. Верхняя граница полного ряда при тех же 50% — 18 ГБ ≈ 3.6 с и по-прежнему выше SLO. Sampling снимает реалистичное чтение, не оценку «прочитали все колонки». Цена: ошибка на узких сегментах воронки, не на DAU.

Пропускная способность **популярного** приложения в query-time — потолок выбранного способа считать воронку, не инфраструктуры приёма. Основание — колоночное чтение ~2.4 с на 90 днях; ~7 с остаётся верхней границей и само по себе вывод не держит.

### Предложения по снижению стоимости

CDN в системе нет, «включить CDN» не рассматриваем. База — месяц года 1, **$4.7k**.

Kafka остаётся 3 брокера — половина потока брокер не снимает | статистическая ошибка на узких шагах воронки и малых приложениях; sampling уже в scope, но 50% — не значение по умолчанию для всех |

### Оптимизации без значимого эффекта для данной системы

- **Урезать Query API или кэшировать дашборд:** 3 RPS, **<2%** compute. Запросов станет меньше, счёт почти не изменится: деньги в ClickHouse и Ingest.
- **4+ шарда ClickHouse с первого дня** — наоборот дороже (ноды ×2), hotspot по `app_id` не ускоряет.
- **Spot на Storage Writer:** десятки долларов, Writer держит единственный путь в SoT.
- **Архив сырых событий в объектное хранилище:** 2.3 ТБ × $0.023 ≈ **$53/мес** экономии диска CH, если вынести; query-time по архиву p95 < 2 с не выполняет, для MVP воронки бесполезно.
