# 1. Требования

> Часть [решения ДЗ 6](README.md). Система: сервис телеметрии мобильных приложений.

Платформа product-аналитики для мобильных приложений: регистрация приложения → SDK получает
конфиг → приём событий → хранение → воронки/retention/DAU-MAU через query API. Не APM и не
сбор произвольных логов: тест на переусложнение — не длина цепочки, а вопрос «относится ли
фича к приёму, хранению, конфигурации или выдаче аналитики зарегистрированного приложения».

## 1.1 Функциональные требования (scope)

1. **Приём батчей событий от мобильного SDK** по HTTPS: проверка схемы события, gzip,
   идемпотентность по `event_id`. SDK отправляет накопленный батч, а не каждое событие
   отдельно — иначе ingest не выдержит объём записи (см. §1.2).
2. **Регистрация приложений и выдача API-ключей.** Без идентификации источника ingest не
   отличит легитимный SDK от произвольного клиента и не применит лимиты per-app.
3. **Конфигурирование определений воронок и метрик per-app.** Владелец приложения задаёт
   шаги воронки и набор атрибутов события; query API считает по этим определениям, а не по
   зашитой в код логике конкретного приложения.
4. **Query API — четыре эндпоинта:** conversion воронки, кривая retention, DAU/MAU, разбивка
   по сегментам (страна / платформа / версия приложения). `platform` и `version` приходят
   от SDK как зарегистрированные атрибуты события; `country` (и тип устройства) Ingest API
   проставляет по offline-базе (IP / User-Agent), без внешнего вызова на hot path — иначе
   сегмент «страна» потребовал бы GeoIP-сервис в критическом пути приёма. Четыре запроса
   закрывают ядро product-аналитики; расширение списка — главный источник scope creep
   (см. §1.4).
5. **Конфиг SDK:** sampling rate и feature flags, которые клиентский SDK забирает при старте
   сессии. Без серверного управления сэмплированием единственный способ снизить пиковую
   нагрузку по событиям — выпуск новой версии приложения.

## 1.2 Нефункциональные требования

Цифры ниже — вход для расчётов в [`sizing.md`](sizing.md). RPS среднее/пик из них выводится,
а не задаётся отдельно: единица нагрузки — событие, а не «запрос пользователя».

| Параметр | Значение | Комментарий |
|---|---|---|
| Приложений-клиентов платформы | 2 000 | Подключённые мобильные приложения, не конечные пользователи. Объём метаданных (ключи, определения воронок) остаётся малым относительно потока событий. |
| MAU (суммарно по приложениям) | 50 000 000 | Конечные пользователи приложений-клиентов. Порядок выбран так, чтобы ingest и колоночное хранилище были узким местом, а не CRUD метаданных. |
| DAU | 8 000 000 | ≈ 16 % от MAU — типичная доля для consumer-mobile, не для ежедневного мессенджера. |
| Событий на DAU в сутки | 40 | Экраны + ограниченный набор custom-событий. Выше — уже полный session replay, ниже — слишком мало для воронок из нескольких шагов. |
| Событий/сутки | 320 000 000 | `DAU × 40`. Базовая единица для RPS, хранилища и bandwidth в [`sizing.md`](sizing.md). |
| Средний размер события (до сжатия) | 0.5 КБ | JSON с фиксированным набором атрибутов. Произвольные нерегистрируемые properties запрещены — иначе кардинальность ломает сжатие и время запроса (см. §1.3). |
| Батч от SDK | до 50 событий или раз в 30 с (что раньше) | Компромисс: меньше HTTP-запросов на ingest, задержка появления события в хранилище остаётся приемлемой для аналитики с горизонтом часы/дни. |
| Retention сырых событий | 90 дней | Горизонт запросов воронки и retention. Дальше сырьё не нужно: тренды DAU/MAU закрываются агрегатами. |
| Retention агрегатов DAU/MAU | 2 года | Долгие тренды без хранения сырых событий за тот же срок. |
| Ingest API latency, p99 | < 300 мс | Приём батча и запись в буфер. Ожидание вставки в аналитическое хранилище в этот SLO не входит: иначе p99 ingest привязан к OLAP-записи. |
| Query API latency, p95 | < 2 с | Аналитический запрос по сырым событиям (воронка/retention/сегменты). Не интерактивный UI с сотнями миллисекунд: такие дашборды вынесены в backlog. |
| Доступность Ingest API | 99.9 % | Потеря приёма — потеря продуктовых данных. SDK повторяет отправку, буфер сглаживает короткий простой, но длительный отказ ingest даёт пропуск в рядах воронок. |
| Доступность Query API | 99.5 % | Внутренний инструмент разработчика/аналитика, не user-facing контур конечного пользователя. Ниже ingest: простой query не теряет события. |
| Peak factor | ×3 | Суточный профиль активности пользователей приложений (утро/вечер), не сезонный пик. Множитель не переносится из другой системы: у product-событий нет «сезона отпусков», концентрация приходится на часы бодрствования аудитории. |

Ограничение схемы события, входящее в NFR: набор атрибутов регистрируется per-app заранее;
событие с незаявленным property ingest отклоняет. Это же ограничение закрывает риск
кардинальности в §1.3.

## 1.3 Риски и ограничения

| Риск | Как проявляется | Почему принят |
|---|---|---|
| Scope creep | Домен узкий (событие, сессия, воронка, retention, сэмплирование). Рост идёт не за счёт новых сущностей, а за счёт фич вокруг ядра (ML, real-time, APM, crash reporting). | Главный риск темы. Митигация — жёсткий backlog в §1.4 и фиксированные четыре query-эндпоинта в §1.1. |
| Высокая кардинальность атрибутов | Много уникальных `user_id` неизбежно; плюс произвольные custom-properties ухудшают сжатие колоночного хранилища и время funnel/retention. | Произвольные properties без регистрации запрещены (§1.2). Высокая кардинальность `user_id` — свойство домена и закладывается в сайзинг сжатия, а не повод менять класс хранилища. |
| Exactly-once на транспорте недостижим | SDK повторяет батч после таймаута, хотя сервер мог уже принять предыдущую попытку. | Идемпотентная вставка / дедуп по `event_id` в окне недавних идентификаторов. За пределами TTL окна редкий дубликат возможен; агрегаты funnel/retention устойчивы к единичным дублям, цена exactly-once на клиенте не окупается. |
| Clock skew на устройстве | `event_time` с устройства сдвигается в прошлое или будущее: ломаются окна воронки/retention и партиции по времени события. | Партиционирование сырых событий — по времени приёма на сервере. `event_time` устройства используется в бизнес-запросах с отсечением значений вне допустимого окна. |
| Буфер ingest — единственная защита записи | При длительном отказе записи в аналитическое хранилище события копятся в топике и после истечения retention топика теряются. | Риск принят: топик держит запас на несколько часов простоя writer. Синхронная запись ingest → OLAP сорвала бы SLO p99 < 300 мс из §1.2. |

## 1.4 Backlog (что не входит в scope)

| Тема | Почему не сейчас |
|---|---|
| ML-рекомендации и anomaly detection | Отдельный продукт поверх уже посчитанных метрик, не звено цепочки `SDK → ingest → хранилище → query API`. |
| Real-time дашборды с sub-second latency | Потребовали бы отдельный stream-слой. Воронка и retention — аналитика с горизонтом часы/дни; p95 query API < 2 с из §1.2 этому горизонту соответствует. |
| APM / трейсинг производительности приложения | Другой домен телеметрии (технические спаны, не product-события): другой SDK, другая модель хранения, другие SLO. |
| Crash reporting как отдельная фича | Смешение с product-аналитикой размывает scope. Либо отдельная тема целиком, либо не входит в MVP. |
| Stream processing «текущего DAU» | Не нужен для четырёх query-эндпоинтов из §1.1: DAU/MAU считаются по сырым событиям и агрегату с retention 2 года. Пересмотр — при декомпозиции сервисов, если появится отдельный SLO на «DAU прямо сейчас». |
