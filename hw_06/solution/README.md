# ДЗ 6. Проектная работа — решение

> Условие: [../Задание.md](../Задание.md).

## Выбранная тема

Сервис телеметрии мобильных приложений.

## Суть сервиса

Разработчик мобильного приложения хочет знать, что происходит с его пользователями: сколько
дошло до оплаты, сколько вернулось на следующий день, сколько активно каждый день. Мобильное
приложение (через встроенный SDK) отправляет в сервис события — экраны, нажатия, покупки.
Сервис принимает поток этих событий, хранит их и по запросу отдаёт готовые метрики: воронку
конверсии, кривую retention, DAU/MAU, разбивку по стране/платформе/версии приложения.

Масштаб: до 2 000 приложений-клиентов, 50 млн конечных пользователей суммарно, 320 млн
событий в сутки (детали — [`requirements.md`](requirements.md)).

Что сервис не делает: не хранит и не показывает бизнес-данные приложения (заказы, платежи,
профили пользователей) — только события, которые разработчик сам решил отправлять для
аналитики. Не занимается техническим мониторингом приложения (сбои, производительность,
трейсинг) — это другой класс телеметрии с другими требованиями и другим SDK.

## Класс телеметрии

Это телеметрия класса **Product / Behavioral analytics**: единица — действие пользователя
в продукте (экран, нажатие, покупка), результат — воронка, retention, DAU/MAU. Знакомый
ориентир класса — Amplitude (рядом Mixpanel). Граница с APM, логами и crash reporting
зафиксирована выше и в [`requirements.md` §1.4](requirements.md#14-backlog-что-не-входит-в-scope):
другой SDK, другая модель хранения, другие SLO.

| | Это решение | Amplitude (SaaS-ориентир класса) |
|---|---|---|
| Данные и инфраструктура | Self-hosted: сырьё и витрины у оператора платформы, retention и схема — свои ([`sizing.md`](sizing.md), [`data-storage.md`](data-storage.md)) | Данные у вендора; retention, квоты событий и sampling задаёт тариф |
| Стоимость на масштабе | ~$0.49 / 1M событий, ~$2.4 / приложение-клиент в месяц ([`sizing.md` §4](sizing.md#4-оценка-ресурсов-и-стоимости)) | Растёт со событиями и «дополнительными» фичами тарифа; потолок квоты — внешнее ограничение |
| Гибкость определений | Query-time по сырью: смена шагов воронки видна на следующем запросе ([ADR-0003](arc42/adr/0003-query-time-vs-pre-aggregation.md)) | Богатый chart/cohort builder; смена определения зависит от модели агрегатов вендора |
| Продукт для владельца | Query API + пороговый webhook ([`api/alerts.md`](api/alerts.md)); UI/дашборд — клиент API, не часть платформы | Готовый UI, cohort/path analysis, session replay, экосистема интеграций и SDK |
| Что сознательно не берём | ML, real-time дашборды, APM, crash reporting ([`requirements.md` §1.4](requirements.md#14-backlog-что-не-входит-в-scope)) | Это как раз сильная сторона SaaS-ориентира |

**Плюсы относительно Amplitude:** владение сырьём и инфраструктурой; предсказуемая цена и
схема на заявленном масштабе; нет vendor lock-in и чужого event quota; мультиарендность
под своим контролем (шард и лимит per `app_id`).

**Минусы относительно Amplitude:** нет готового UI, когорт, session replay, SDK «из коробки»
под все платформы и экосистемы интеграций; нет ML/anomaly detection. Это не пробел модели,
а граница MVP: узкое ядро с проверяемыми SLO вместо продукта «под ключ».
