# 7. Безопасность

> Часть [решения ДЗ 6](README.md). Система: сервис телеметрии мобильных приложений
> (контейнеры — [`architecture/`](architecture/), контракты — [`api/`](api/),
> хранилища — [`data-storage.md`](data-storage.md)). Схема контуров —
> [`diagrams/auth-planes.puml`](diagrams/auth-planes.puml).

Два клиентских контура уже разведены в декомпозиции: отдельного API Gateway нет, потому что
у Ingest (SDK, API-ключ) и у App & Config / Query API (владелец, JWT) разные клиенты и
разная модель авторизации
([`arc42/04-solution-strategy.md` §4.2](arc42/04-solution-strategy.md#42-декомпозиция-сервисов)).
Ниже фиксируем это как контур безопасности, не вводим параллельный механизм.

## 1. Аутентификация / авторизация

| Клиент | Где | Механизм | Авторизация |
|---|---|---|---|
| Mobile App + SDK | Ingest `POST /v1/events`; App & Config `GET /v1/sdk/config` | `X-Api-Key`, lookup по `key_hash` (Redis; при промахе — App & Config → PostgreSQL) | ключ — identity приложения, не пользователя; rate-limit per-`app_id` |
| Владелец приложения | App & Config / Query API | `Authorization: Bearer <jwt>` внешнего IdP; проверка подписи, срока, scope по JWKS | роль `app_owner`: только свои `appId` (`owner_id` из `sub` токена) |

**Почему не один JWT на оба контура.** SDK — встроенный клиент в мобильном приложении
владельца: у конечного пользователя нет учётной записи платформы, а батч должен уложиться
в p99 < 300 мс
([`requirements.md` §1.2](requirements.md#12-нефункциональные-требования)). Подпись и
проверка JWT на каждый ingest-запрос добавили бы зависимость от IdP на hot path приёма
(Tier 0) без выигрыша: идентифицировать нужно приложение, а не человека. API-ключ —
секрет приложения; JWT — сессия владельца в дашборде.

**Lookup ключа.** В PostgreSQL хранится `api_keys.key_hash`, не plaintext
([`diagrams/er-data-model.puml`](diagrams/er-data-model.puml)). Ingest хеширует предъявленный
`X-Api-Key` и ищет по хешу в Redis, при промахе — в App & Config. В значении кэша —
`app_id`, схема, status, лимиты; сам секрет в Redis не кладётся. Plaintext ключа
возвращается владельцу один раз при создании или ротации
([`api/app-registration.md`](api/app-registration.md)); повторный просмотр невозможен.

**Ролевая модель.** Продуктовая роль одна — `app_owner`. В требованиях у приложения один
владелец (`apps.owner_id`); команды и иерархия ролей не введены — это отдельный контур
доступа, которого нет в scope. SDK ролью не является: это технический клиент с identity
приложения. Платформенный ops (cutover DR, restore бэкапа) работает вне продуктового API —
доступы и секреты региона B, [надёжность §4](reliability.md#4-план-dr).

**Авторизация владельца — не IDOR.** `appId` берётся из пути и сверяется с `owner_id` из
`sub` токена, а не из тела запроса: иначе чужой `appId` в body позволил бы прочитать воронку
или сменить ключи чужого приложения ([`api/analytics-query.md`](api/analytics-query.md),
[`api/definitions.md`](api/definitions.md) — `403 FORBIDDEN`). Тот же принцип, что
`guestProfileId` из токена, а не из body, в Bookly-аналоге.

**JWT выпускает внешний IdP, не контейнер продукта.** Identity в C2 нет и не добавляется:
логин/пароль владельца — не часть цепочки «регистрация приложения → ingest → аналитика»,
свой Identity-сервис дал бы ещё один контейнер и SoT учёток без выигрыша на hot path.
App & Config и Query API проверяют токен локально по JWKS IdP; JWKS кэшируется с TTL до
ротации, чтобы не ходить в IdP на каждый запрос. Иначе недоступность внешнего IdP блокировала
бы уже залогиненных владельцев (CRUD ключей, Query API) — при том, что приём событий от этого
контура не зависит.

**Вебхуки внешних систем.** Не применимо: inbound-вебхуков нет. Нечего подписывать
`X-Provider-Signature` и не от кого принимать чужой event id — в отличие от платёжного
провайдера в Bookly-аналоге.

**Сервис-сервис.** Сеть внутри кластера не считается доверенной потому, что трафик «внутри
периметра». Внутренние HTTP (Ingest → App & Config на промахе кэша, Query API → App & Config
за definitions) — mTLS плюс короткоживущий service identity, не пользовательский JWT:
App & Config проверяет, что вызов пришёл от Ingest или Query API, а не от любого пода,
получившего сетевой доступ. Отдельный gRPC-слой под это не заводится — синхронных
многошаговых команд между сервисами нет
([`arc42/04-solution-strategy.md` §4.3](arc42/04-solution-strategy.md#43-протоколы--микс));
меняется только транспортное доверие на уже существующих HTTP-рёбрах. Kafka, ClickHouse,
PostgreSQL, Redis — TLS и учётные данные из секрет-хранилища, не открытое соединение.

**Окно отзыва API-ключа.** Штатно отозванный ключ принимается до истечения TTL кэша (5 мин,
[`data-storage.md` §4](data-storage.md#4-кэширование)) — принятый trade-off против
синхронного Postgres на каждый батч. При деградации App & Config окно расширяется до 30 мин
stale-кэша ([ADR-0005](arc42/adr/0005-ingest-config-degraded-mode.md)): иначе Tier 1-сбой
эскалирует в потерю событий на Ingest. Не fail-open без проверки ключа (неизвестный `app_id`
отклоняется сразу) и не мгновенный revoke ценой p99 ingest. Ротация — операция владельца,
не платформы.

## 2. Шифрование и управление секретами

- **В транзите** — TLS 1.2+ на публичных HTTPS (SDK ↔ Ingest / App & Config, владелец ↔
  App & Config / Query API). Внутри периметра: mTLS на HTTP-рёбрах сервисов ([п.1](#1-аутентификация--авторизация));
  TLS к Kafka, ClickHouse, PostgreSQL, Redis. Трафик не считается доверенным по умолчанию
  потому, что он «внутри кластера».
- **At rest** — disk-level encryption managed-томов PostgreSQL, ClickHouse, Kafka, Redis
  (Tier 0/1 из [надёжности §1](reliability.md#1-rto--rpo-по-сервисам)). Полевое шифрование
  строк `events` не добавляем: при той же модели угроз (компрометация диска/снапшота) оно
  не даёт защиты сверх disk-level, но ломает колоночное сжатие и скан, от которых зависит
  p95 Query API < 2 с ([`sizing.md`](sizing.md), [ADR-0003](arc42/adr/0003-query-time-vs-pre-aggregation.md)).
- **API-ключи — не шифруем, а хешируем** (SHA-256 / HMAC от plaintext). Шифрование обратимо
  при компрометации ключа шифрования, хеш — нет. bcrypt/argon2 здесь не берём: ключ уже
  высокоэнтропийный (CSPRNG при выдаче), а медленный KDF на каждый ingest-батч не
  укладывается в p99 < 300 мс. Plaintext живёт только в ответе create/rotate и в памяти
  Ingest на время запроса. Пароли владельца платформа не хранит — их хеширует внешний IdP.
- **Сокращаем поверхность, а не только шифруем.** Отсутствие данных на диске сильнее любого
  шифрования: то, чего нет в базе, не компрометируется независимо от качества шифрования.
  Не храним: plaintext API-ключа; сырой IP клиента (Ingest проставляет `country` /
  `device_type` по offline-базе, IP в событие не пишет); заказы, платежи, профили конечных
  пользователей приложения — это не предмет телеметрии
  ([`README.md`](README.md#суть-сервиса)). `user_id` в `events` — непрозрачный идентификатор,
  который SDK прислал как стабильный ключ воронки/retention; на ingest его не хешируем:
  сломается join владельца со своей CRM и устойчивость когорт, а произвольный PII
  (email, телефон) и так не проходит ingest без регистрации в `event_schema`
  ([`requirements.md` §1.3](requirements.md#13-риски-и-ограничения)).
- **Бэкапы** — шифрованы, отдельный аккаунт, доступ read-only для восстановления; уже
  зафиксировано в [надёжности §2](reliability.md#2-репликация-критичных-хранилищ). Если это
  тот же доступ, что и прод, компрометация прода становится компрометацией бэкапа — «1 копия
  вне площадки» превращается в фикцию.
- **Секреты** (пароли PostgreSQL / ClickHouse / Redis, credentials Kafka, клиентские
  сертификаты mTLS) — в секрет-хранилище (Vault/аналог), не в переменных окружения и не в
  конфигах открытым текстом. Ротация: API-ключи — владельцем ([п.1](#1-аутентификация--авторизация));
  подпись JWT — на стороне IdP, локальный кэш JWKS не требует перевыпуска всех сессий
  одновременно; credentials хранилищ и сертификаты mTLS — ротация из секрет-хранилища,
  без перевыпуска пользовательских ключей.
