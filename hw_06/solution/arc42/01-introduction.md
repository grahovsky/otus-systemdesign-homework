# 1. Introduction and goals

> Часть [решения ДЗ 6](../README.md).

## Требования / цели (G1–Gn)

Каждая цель закрывает один аспект [ключевого вызова](../README.md#ключевой-вызов):
G1 — аналитика по своему сырью, без чужой витрины; G2 — приём не ждёт OLAP-вставку;
G3 — ретраи SDK не требуют exactly-once на транспорте; G4 — фиксированная схема события,
а не произвольный JSON в колонках.

| # | Цель | Метрика / критерий |
|---|---|---|
| G1 | Владелец приложения получает funnel/retention/DAU-MAU без интеграции с чужим SoT | 4 query-эндпоинта, latency p95 < 2 с ([`../requirements.md`](../requirements.md#12-нефункциональные-требования)) |
| G2 | Приём событий не деградирует под пиковой нагрузкой | Ingest API p99 < 300 мс при peak factor ×3 |
| G3 | Дубликаты/ретраи SDK не искажают аналитику | Идемпотентная вставка по `event_id`, а не exactly-once на транспорте |
| G4 | Кардинальность атрибутов не превращает ClickHouse в узкое место | Фиксированный, регистрируемый per-app набор атрибутов события |

## Акторы

| Актор | Зачем обращается |
|---|---|
| **Владелец приложения** (person) | Регистрирует приложение и API-ключи, настраивает funnel/metric definitions, sampling и пороговые алерты, читает аналитику через Query API, получает webhook при срабатывании правила |
| **Mobile App + SDK** (external system) | Технический источник событий — не сам конечный пользователь приложения, а встроенный SDK: батчит и отправляет события, тянет конфиг sampling/feature flags |

## Масштаб (порядок величины)

320 000 000 событий/сутки (8M DAU × 40), 50M MAU, 2 000 приложений-клиентов. Детальные
расчёты RPS/хранилища/bandwidth — в [`../sizing.md`](../sizing.md), исходные цифры — в
[`../requirements.md` §1.2](../requirements.md#12-нефункциональные-требования).
