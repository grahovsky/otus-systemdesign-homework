# ADR-0005 — Деградация Ingest API при недоступности App & Config: stale-cache вместо fail-closed

- **Status**: Accepted
- **Date**: 2026-09-12
- **Decision makers**: архитектор

## Context

Ingest API держит cache-aside кэш API-ключа/схемы события/sampling в Redis с TTL 5 мин
([`../../data-storage.md` §4](../../data-storage.md#4-кэширование)). При промахе кэша Ingest
синхронно ходит в App & Config (PostgreSQL) — это часть бюджета p99 < 300 мс
([`../../requirements.md` §1.2`](../../requirements.md#12-нефункциональные-требования)).

App & Config отнесён к Tier 1 в [`../../reliability.md` §1](../../reliability.md#1-rto--rpo-по-сервисам):
его простой не теряет уже принятые события и допускает RTO 10 мин (локально) / 30 мин (DR).
Но Ingest API — Tier 0: событие, не принятое во время простоя, теряется навсегда (SDK не
хранит неотправленные батчи бесконечно). Без дополнительного решения деградация App & Config
эскалировала бы в потерю событий на Ingest сразу, как только истечёт TTL кэша (до 5 минут
после начала инцидента) — то есть Tier 1-сбой стал бы фактическим Tier 0-сбоем на смежном
компоненте, при этом сам Ingest API и Kafka продолжали бы работать штатно.

Варианты: (а) fail-closed — отклонять батч при промахе кэша и недоступном App & Config;
(б) fail-open без ограничения — принимать батч без проверки ключа/схемы; (в) fail-open
ограниченно — обслуживать запрос из просроченного, но ранее закэшированного значения, пока
деградация не превысит заданный бюджет.

## Decision

Ingest API продолжает использовать закэшированное (пусть и просроченное по TTL) значение
ключа/схемы/sampling, если fallback-вызов к App & Config при промахе не удался (timeout,
5xx, открытый circuit breaker), — но не дольше **30 минут** сверх обычного TTL 5 мин. После
превышения 30-минутного окна деградации Ingest переходит к fail-closed для этого `app_id`:
отклоняет батч кодом, который SDK трактует как временную ошибку и повторяет позже (в рамках
собственного бюджета ретраев).

Circuit breaker на пути Ingest → App & Config открывается после серии неудачных попыток и
не даёт retry storm добивать уже деградировавший App & Config: при открытом breaker Ingest
сразу берёт stale-значение из кэша, не тратя таймаут на каждый запрос.

30 минут выбраны не произвольно: это больше RTO App & Config при локальном отказе (10 мин,
[`../../reliability.md` §1](../../reliability.md#1-rto--rpo-по-сервисам)) с запасом, и
совпадает по порядку с RTO при региональном DR (30 мин) — то есть при большинстве реальных
сценариев отказа App & Config Ingest успевает пережить простой полностью прозрачно для уже
известных приложений, ничего не теряя.

Ограничение действует только на **уже закэшированные** `app_id`. Приложение, впервые
обратившееся в момент простоя App & Config (нет записи в кэше), обслуживается fail-closed
сразу — безопасного значения по умолчанию для незнакомого ключа/схемы не существует.

## Consequences

### Позитивные

- Инцидент Tier 1 (App & Config) в подавляющем большинстве случаев не превращается в потерю
  событий на Ingest — деградация остаётся локализованной там, где случилась.
- Circuit breaker снимает нагрузку retry-штормом с уже деградировавшего App & Config, ускоряя
  его восстановление.

### Негативные / trade-offs

- Отозванный API-ключ или изменённая схема события применяются с задержкой до 30 минут в
  худшем случае (App & Config недоступен именно в момент ротации/смены) — это шире обычного
  окна в 5 мин TTL, принятого как штатный trade-off ([`../../data-storage.md` §4](../../data-storage.md#4-кэширование)).
- Новые приложения (без записи в кэше) не защищены этим механизмом и продолжают зависеть
  от доступности App & Config напрямую.

### Риски

- Если App & Config недоступен дольше 30 минут для многих приложений одновременно, Ingest
  массово переходит в fail-closed — деградация становится видимой резко, а не плавно.
  Митигация — это же событие уже покрыто алертом на доступность App & Config
  ([`../../reliability.md`](../../reliability.md)), реакция должна начаться раньше порога.

## Alternatives considered

### Fail-closed сразу при промахе (вариант а)

Простое поведение, без дополнительной логики. Отклонено: превращает любой простой App & Config
(Tier 1, RTO минуты) в потерю событий на Ingest (Tier 0) уже через 5 минут — именно тот
сценарий, которого спроектированная развязка Ingest/App & Config должна избегать.

### Fail-open без ограничения по времени (вариант б)

Убирает риск потери событий полностью, но отозванный ключ или удалённое приложение продолжают
приниматься бессрочно при затяжном инциденте App & Config — риск растёт без верхней границы и
не привязан к RTO самого App & Config. Отклонено как неограниченное решение без компенсирующего
контроля.
