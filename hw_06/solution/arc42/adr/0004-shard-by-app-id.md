# ADR-0004 — Шардирование ClickHouse по `app_id`, не по `hash(user_id)`

- **Status**: Accepted
- **Date**: 2026-09-09
- **Decision makers**: архитектор

## Context

Сырые события в ClickHouse растут на 90-дневном окне до нескольких терабайт
([`../../sizing.md` §2](../../sizing.md)), insert-поток в пике — 11 111 событий/с
([`../../sizing.md` §1](../../sizing.md)). Кластер должен горизонтально расти, но три из
четырёх query-эндпоинтов (funnel, retention, сегменты) всегда фильтруют по одному `appId`
из пути запроса ([`../../api/analytics-query.md`](../../api/analytics-query.md)) — запрос
никогда не агрегирует события нескольких приложений сразу.

## Decision

Шардируем `events` по `app_id` (`ORDER BY (app_id, event_time)` на каждом шарде), а не по
`hash(user_id)`. Старт — 2 шарда × 2 реплики.

## Consequences

### Позитивные

- Запрос funnel/retention/сегментов по одному `appId` попадает в один шард без
  scatter-gather и слияния промежуточных результатов координатором.
- Партиционирование по времени приёма внутри шарда ([ADR-0001](0001-batch-insert-clickhouse.md))
  работает как обычно.
- Добавление шардов линейно снижает диск и insert-нагрузку на реплику для среднего
  приложения (160k событий/сутки, `~0.9 ГБ` сжатых за 90 дней — доли секунды скана).

### Негативные / trade-offs

- Самое нагруженное приложение (до 2 % потока, [`../../sizing.md` A14](../../sizing.md))
  целиком лежит на одном шарде: добавление шардов не ускоряет его запрос. При
  `~36 ГБ` сжатых на 90 дней последовательный скан на NVMe (`~5 ГБ/с`) даёт `~7 с` — выше
  SLO p95 < 2 с ([`../../requirements.md` §1.2](../../requirements.md#12-нефункциональные-требования)).
  Митигация для этого приложения — вне текущего ADR: pre-aggregation по исключению,
  sampling конфига SDK или изменение схемы для конкретного клиента
  ([`../../sizing.md` §5](../../sizing.md)).
- Распределение по `app_id` не гарантирует равномерность между шардами (2 000 приложений
  разного размера) — нужен явный биннинг по объёму при ре-балансировке, не round-robin
  по id.

### Риски

- Рост числа крупных приложений одновременно на одном шарде создаёт совокупный hotspot
  шарда, не только одного `app_id`. Митигация — мониторинг объёма insert/скана на шард и
  ручной re-pin крупных `app_id` на отдельный шард при превышении порога.

## Alternatives considered

### Шардирование по `hash(user_id)`

Распределяет события каждого приложения равномерно по всем шардам — снимает hotspot
крупного приложения (при 4 шардах скан hotspot падает с `~7 с` до `~1.8 с`,
[`../../sizing.md` §5](../../sizing.md)). Отклонено как базовая стратегия: funnel/retention/
сегменты запросы **всегда** ограничены одним `appId`, при этом каждый запрос среднего
приложения (99.9 % трафика по объёму) стал бы scatter-gather по всем шардам вместо одного —
средний случай платит за хвостовой. Остаётся кандидатом как точечная эскалация для
конкретных hotspot-приложений, не как замена ключа для всех.

### Без шардирования (вертикаль + реплики на чтение)

Не проходит горизонт роста: диск сырья к 3 году — `~9.4 ТБ` на реплику
([`../../sizing.md` §2](../../sizing.md)), insert-поток растёт линейно с потоком событий.
Реплики на чтение размножают одну и ту же копию, не снимают объём на ноде.
